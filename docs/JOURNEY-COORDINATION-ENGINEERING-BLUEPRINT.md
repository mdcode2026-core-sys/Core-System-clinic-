# CORE SYSTEM — Journey Coordination Engineering Blueprint

**Status:** Final pre-implementation engineering reference — reconciled with PJ, Workforce & Operations, Financial & Resources, Team & Access, Communications, Agenda, Clinical, Treatment Plan, Follow-up, Patient Portal and Insights.
**Domain:** Journey Coordination
**Scope:** Tenant / Clinic operating environment
**Authority:** This document governs Journey Coordination unless a later explicit architectural decision supersedes it.

## 1. Product position

Journey Coordination is the clinic-wide work-coordination layer. It connects work generated by existing domains without replacing or duplicating those domains.

It is not a task-management product, not a second Agenda, not a second Follow-up engine, not a second Communications system, and not a second Patient Journey.

The target is simple daily operation with deeper coordination logic in the background.

## 2. Core principle

```text
Existing Domain Event
 → Required Work
 → Identify capable/authorized actor
 → Assign / Request / Handoff
 → Execute
 → Notify when appropriate
 → Monitor
 → Escalate when required
 → Close
 → Analyze
```

The user should see only the work relevant to them. The system may maintain substantially richer state and history in the background.

## 3. Domain boundaries

Journey Coordination owns:

- General work items.
- Tasks.
- Operational requests.
- Assignment and ownership state.
- General handoffs.
- General next actions.
- Coordination-level priority and expected completion.
- Escalation state.
- My Work / Work Center presentation.
- Coordination automation.
- Coordination audit/history.

Journey Coordination does **not** own:

- Appointment scheduling — Agenda.
- Patient clinical care — Clinical domains.
- Treatment plan definition — Treatment Plan.
- Patient follow-up clinical/business logic — Follow-up domain; Coordination integrates with it.
- System authorization — Team & Access.
- Employment/availability/leave/payroll — Workforce & Operations.
- Financial rules — Financial & Resources.
- Inventory/purchasing master logic — Financial & Resources.
- Messaging/notification transport — Communications.
- Analytics/KPIs — Insights.
- Patient account experience — Patient Portal.

## 4. Work Item model

Internally, different forms of work may share a common coordination model while preserving their own domain-specific semantics.

```text
Work Item
├── Task
├── Request
├── Handoff
├── Follow-up-linked work
├── Next Action
└── Escalation state
```

These are not required to appear as separate products in the UI.

The principal user-facing concept should be **My Work / Work Center**.

## 5. Task — Core

A Task means:

> Someone is expected to perform an action.

Core attributes:

- Title / action.
- Context.
- Owner / assignee.
- Status.
- Priority.
- Expected/due time.
- Source event/domain.
- Optional patient/visit/appointment/treatment/financial/resource context.
- Notes.
- Completion evidence where required.
- Audit history.

Tasks must be able to originate manually or from approved domain events.

## 6. Request — Core

A Request is distinct from a Task.

It allows a user to ask another authorized actor to perform an action the requester cannot or should not execute directly.

Example:

```text
Reception
 → Request inventory action
 → Authorized inventory user
 → Execute
 → Request closed
```

Requests must respect effective permissions and must never provide an authorization bypass.

## 7. Handoff — Core

A Handoff represents a meaningful transfer of responsibility, not merely an assignee change.

A handoff may include:

- Source owner.
- Destination owner/team/workspace.
- Reason.
- Context.
- Previous work.
- Current status.
- Acceptance/rejection where required.
- Timestamp.
- Audit trail.

Existing Clinical → Reception handoff behavior must be reused and generalized only where genuinely required; the Clinical workflow remains the owner of its clinical-specific lifecycle.

## 8. Follow-up and Next Action

Follow-up remains its own domain capability.

Journey Coordination integrates with Follow-up rather than rebuilding it.

```text
Follow-up
 → Next Action
 → Work / Task when an operational action is required
```

A follow-up is patient-continuity work; a general Task can concern any clinic operation.

## 9. Escalation

Escalation means that work requires attention beyond the current handling path.

### Core

- Manual escalation.
- Escalation reason.
- Escalation target.
- Timestamp.
- Audit trail.

### Advanced

- Time-based escalation.
- Priority-based escalation.
- Automated escalation chains.
- Rule-based escalation.

Escalation must not silently grant permissions.

## 10. Permission-aware coordination

Team & Access remains the authorization source of truth.

Roles and permissions remain independent.

Coordination may evaluate effective permissions to determine who can execute an action, but it must not create or modify permissions.

```text
Work
 ↓
Required Action
 ↓
Effective Permission
 ↓
Eligible Actors
```

Read access is not execution authority.

Where a user can see but cannot execute, the system may offer an appropriate Request or Handoff path if permitted.

## 11. Workforce integration

Workforce remains separate from Coordination.

Workforce provides information such as:

- Staff identity/employment context.
- Availability.
- Working pattern.
- Leave/absence.
- Capacity.
- Skill/Capability when enabled.

Coordination may use these inputs for assignment and routing.

Basic assignment must not require advanced Skills or capacity optimization.

Advanced routing may consider:

```text
Permission
 + Availability
 + Capacity
 + Skill/Capability
 + Current workload
 → Suitable actor
```

## 12. Agenda integration

Agenda remains the canonical appointment scheduler.

Coordination must never become a second calendar or appointment engine.

Agenda events may generate operational work:

```text
Appointment confirmed
 → Preparation required
 → Task
```

or:

```text
Appointment completed
 → Required operational action
 → Work Item
```

Coordination does not own booking availability or appointment lifecycle.

## 13. Clinical and Patient Journey integration

Coordination is not part of PJ ownership. It supports PJ when operational work is related to patient care.

Examples:

```text
Treatment Plan
 → Procedure scheduled
 → Preparation Task
```

```text
Clinical work completed
 → Administrative action
 → Task / Handoff
```

```text
Follow-up due
 → Follow-up domain
 → Operational action if required
```

The system must not duplicate clinical states inside generic tasks when the clinical domain already owns the authoritative state.

## 14. Financial & Resources integration

Financial, inventory, purchasing and resource domains remain authoritative for their own records.

They may emit work:

```text
Low stock
 → Purchase Request
 → Coordination
 → Purchasing
```

```text
Financial exception
 → Required review
 → Work Item
```

Coordination stores the work state, not the financial or inventory truth.

## 15. Communications integration

Communication is not equivalent to work.

A message may create or update work when an explicit operational action is required.

```text
Communication
 → Request / Task
 → Action
 → Completion communication
```

Conversely, work completion may trigger an appropriate notification or message through Communications.

No second messaging system may be created inside Coordination.

## 16. Patient Portal integration

Patient Portal remains the patient-facing domain.

Portal activity may generate clinic work:

```text
Patient request
 → Coordination work
 → Staff action
 → Portal communication
```

Clinic work may also request patient action through the Portal.

Patient-facing clinical/financial information remains governed by the relevant domains and Portal access rules.

## 17. My Work / Work Center — Core

The primary user-facing coordination surface should be simple.

It should expose relevant categories such as:

- Due today.
- Overdue.
- Requests.
- Waiting for me.
- Waiting for others.
- Handoffs.
- Follow-ups requiring action.
- Escalated work.

The system should avoid forcing users to understand internal workflow terminology.

## 18. Clinic Admin Oversight

Clinic Admin requires a broader operational view because the Admin is responsible for the clinic's operation and has the authority granted by the tenant's access model.

Useful views include:

- Unassigned work.
- Overdue work.
- Blocked work.
- Escalations.
- Workload distribution.
- Handoff delays.
- Repeated operational bottlenecks.
- Completion performance.

This is operational oversight, not automatic access to every protected clinical or patient detail.

## 19. Automation

Automation should be event-driven and remain in the background.

```text
Event
 → Rule
 → Work Item
 → Routing
 → Notification
 → Monitoring
 → Escalation if required
```

### Core

- Approved event-to-task/request creation.
- Reminders.
- Basic routing.
- Basic status transitions.

### Advanced

- Rule-based routing.
- Automated handoffs.
- Automated escalation.
- Conditional workflows.
- Recurring work.

Automation must respect tenant configuration, entitlements, permissions and domain ownership.

## 20. Priority and expected completion

CORE SYSTEM should use a simple operational model rather than enterprise ITSM-style SLA complexity.

Core:

- Priority.
- Expected/due completion.
- At-risk state where useful.
- Overdue state.

Advanced:

- Rule-based targets.
- Automatic escalation.
- Operational performance analysis.

## 21. Skill / Capability

Skill / Capability remains an Advanced Team & Access / Workforce capability and must not become a permission substitute.

```text
Role       = organizational label
Permission = authorization
Skill     = capability/qualification
```

Coordination may use Skills in advanced routing, but basic operation must remain functional without them.

## 22. Data foundation and future AI

Coordination should capture structured historical data from day one:

- Source event.
- Required action.
- Assignee/owner.
- Assignment changes.
- Requester.
- Handoffs.
- Status transitions.
- Expected vs actual completion.
- Delays.
- Escalations.
- Related domain context.
- Communication events where relevant.
- Permission/authorization outcome.
- Workforce context where appropriate.
- Completion evidence.

This creates a strong foundation for future automation, Insights and AI agents without requiring those capabilities in the basic user experience.

## 23. Insights integration

Coordination generates operational data; Insights owns its interpretation.

Examples:

```text
Coordination data
 → Insights
 → KPI / trend
 → Operational decision
```

No duplicate Coordination analytics engine should be created.

## 25. Non-goals

Journey Coordination will not become:

- A project-management suite.
- An enterprise ITSM platform.
- A second appointment scheduler.
- A second patient journey engine.
- A second clinical workflow engine.
- A second messaging system.
- A second HR/workforce system.
- A second analytics system.

## 26. Control requirements

Coordination must never weaken:

- Tenant isolation.
- Effective permission enforcement.
- Approval boundaries.
- Auditability.
- Clinical safety boundaries.
- Financial controls.
- Legal/compliance requirements.
- Separation of duties where required.
- Patient privacy.

## 27. Final reconciliation decisions

1. Journey Coordination is a clinic-wide work-coordination layer, not a standalone task-management product.
2. Existing domains remain authoritative for their own records and lifecycles.
3. Team & Access remains the authorization source of truth.
4. Roles remain independent from permissions.
5. Workforce remains independent from Agenda and Coordination.
6. Agenda remains the canonical appointment scheduler.
7. Follow-up remains a distinct patient-continuity capability and is integrated rather than duplicated.
8. Communications remains the communication layer; messages are not automatically tasks.
9. Requests are a first-class Core concept for permission-aware operational collaboration.
10. Handoffs represent meaningful responsibility transfer, not every assignment change.
11. Clinic Admin receives operational oversight without turning Coordination into unrestricted patient-data access.
12. Basic UI remains simple; deeper routing, automation, workload and intelligence remain background capabilities.
13. Skills/Capabilities are Advanced and are not a permission mechanism.
14. Coordination data must be structured for Insights and future AI from day one.
15. Financial, administrative, clinical, legal and privacy controls always take precedence over convenience.

## 28. Implementation rule

```text
Approved Coordination Contract
 → Inspect existing domain behavior
 → Reuse authoritative records
 → Extend only where a genuine coordination gap exists
 → Integrate through explicit events/actions
 → Enforce effective permissions
 → Validate cross-domain behavior
 → Preserve simple UX
 → Capture structured operational history
 → Validate runtime
```

No duplicate domain engine may be introduced merely to make coordination easier.
