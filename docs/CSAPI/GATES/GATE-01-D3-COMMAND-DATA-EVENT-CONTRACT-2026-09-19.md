## 1. Authority boundary

D3 owns lifecycle write authority for Patient Flow over the D2 foundations.

The canonical mutation path is:

```
UI / existing server action
        ↓
thin D3 server adapter
        ↓
canonical D3 database command
        ↓
atomic legacy Visit + D2 projections + Event
```

No client or UI path may directly mutate the lifecycle state after its caller is migrated.

No second Patient Flow engine is permitted.

## 2. Canonical lifecycle

```
waiting
   ↓
in_consultation
   ↓
pending_close
   ↓
completed
```

Terminal alternatives:
- waiting → no_show
- waiting → cancelled
- in_consultation → cancelled
- pending_close → cancelled

`completed`, `cancelled`, and `no_show` are terminal.

`pending_close` is Visit-only.

The following are not new Visit lifecycle states:
- Work Session `held`
- Work Session `transferred`

They are Work Session outcomes/segments and remain separate from Visit state.

## 3. Command contract

All commands are PostgreSQL functions executed through the authenticated server path.

Common input:
- `p_correlation_id uuid` — client/request correlation key; generated by caller when not already provided.
- The command derives the tenant and actor from the authenticated session. Tenant identity is never accepted as caller-controlled input.

Common result:
```json
{
  "command": "…",
  "tenant_id": "…",
  "visit_id": "…",
  "previous_status": "…",
  "new_status": "…",
  "work_session_id": "… | null",
  "queue_entry_id": "… | null",
  "event_id": "…",
  "correlation_id": "…"
}
```

### 3.1 `csapi_d3_enter_waiting`

Inputs:
- `p_visit_id uuid`
- `p_lane_key text` default `general`
- `p_priority_class text` default `normal`
- `p_entry_reason text` default `arrival`
- `p_routing_target text` nullable
- `p_correlation_id uuid`

Authorization:
- effective `patient_flow:operations`
- effective `sessions:update`

Allowed source states:
- a new/arriving Visit path;
- an existing Visit that is not terminal and has no active Queue Entry, when the existing application flow legitimately needs to establish Waiting.

Result:
- Visit becomes `waiting`;
- exactly one active Queue Entry exists;
- one `waiting_entered` Event is emitted.

Idempotency:
- an already-waiting Visit with the same correlation key returns the existing transition result rather than creating duplicate records;
- the active Queue Entry uniqueness invariant remains the final database guard.

### 3.2 `csapi_d3_reorder_waiting`

Inputs:
- `p_queue_entry_id uuid`
- `p_target_position integer`
- `p_target_lane_key text` nullable
- `p_routing_target text` nullable
- `p_correlation_id uuid`

Authorization:
- effective `patient_flow:operations`
- effective `sessions:update`

Allowed source:
- Queue Entry must be active and belong to a Visit currently in `waiting`.

Behavior:
- persists Reception-defined order;
- optionally changes queue lane/routing metadata using existing Queue lane semantics;
- renumbers the affected active queue to a deterministic contiguous ordering starting at 1;
- never changes Visit status to `in_consultation`;
- never creates a Work Session.

Event:
- `waiting_reordered`.

The existing Queue Engine remains the validation/rules authority for queue behavior; D3 only provides the transactional persistence boundary.

### 3.3 `csapi_d3_start_clinical_work`

Inputs:
- `p_visit_id uuid`
- `p_correlation_id uuid`

Authorization:
- effective `patient_flow:clinical`
- effective `sessions:update`

Responsibility rule:
- the actor must be the canonical Visit provider (`clinic_visit_sessions.doctor_id`) when a provider is assigned;
- existing approved administrative override may be used only where the current permission model explicitly allows it;
- no new room-user assignment model is introduced.

Behavior:
1. lock/re-read the Visit;
2. require current state `waiting`;
3. validate clinical transition through the canonical transition rules;
4. close the active Waiting Queue Entry;
5. create exactly one active Work Session with the authenticated actor as performer and the Visit's existing provider/room context;
6. set Visit to `in_consultation` and preserve existing compatibility timestamps/lock fields;
7. emit one `clinical_started` Event.

Concurrency:
- competing starts on the same Visit cannot both create an active Work Session;
- the D2 partial unique active-Work-Session index remains a hard database guard.

### 3.4 `csapi_d3_finish_clinical_work`

Inputs:
- `p_visit_id uuid`
- `p_correlation_id uuid`

Authorization:
- effective `patient_flow:clinical`
- effective `sessions:update`

Actor rule:
- the active Work Session performer owns the clinical finish;
- the existing explicit administrative override may finish only when the canonical permission engine authorizes it.

Precondition:
- Visit is `in_consultation`;
- an active Work Session exists for the Visit.

Behavior:
1. lock/re-read Visit and active Work Session;
2. update Work Session to `finished` with outcome `finish`, ended timestamp and incremented version;
3. release clinical ownership fields on Visit;
4. set Visit to `pending_close`;
5. create one active reception Queue Entry with `lane_key=general` and `routing_target=reception`;
6. emit one `clinical_finished` Event.

No Agenda state is changed by this command; Agenda retains its own bounded-context ownership.

### 3.5 `csapi_d3_complete_reception`

Inputs:
- `p_visit_id uuid`
- `p_correlation_id uuid`

Authorization:
- effective `patient_flow:operations`
- effective `sessions:close`

Precondition:
- Visit is `pending_close`;
- an active reception Queue Entry exists.

Behavior:
1. lock/re-read Visit;
2. close the active reception Queue Entry;
3. set Visit to `completed`;
4. preserve existing completion timestamp semantics;
5. emit one `reception_completed` Event.

### 3.6 `csapi_d3_cancel_patient_flow`

Inputs:
- `p_visit_id uuid`
- `p_reason text` nullable
- `p_correlation_id uuid`

Allowed states:
- `waiting`
- `in_consultation`
- `pending_close`

Authorization:
- effective Patient Flow permission appropriate to the current context;
- `sessions:update`;
- clinical cancellation remains subject to clinical ownership/override rules.

Behavior:
- set Visit to `cancelled`;
- close any active Queue Entry;
- if an active Work Session exists, set it to `cancelled` and close it;
- emit `cancelled`.

### 3.7 `csapi_d3_mark_no_show`

Inputs:
- `p_visit_id uuid`
- `p_reason text` nullable
- `p_correlation_id uuid`

Authorization:
- effective `patient_flow:operations`
- effective `sessions:update`

Precondition:
- Visit must be `waiting`.

Behavior:
- set Visit to `no_show`;
- close the active Queue Entry;
- emit `no_show`.

## 4. Event taxonomy

D3 standardizes these event types:
- `waiting_entered`
- `waiting_reordered`
- `clinical_started`
- `clinical_finished`
- `reception_completed`
- `cancelled`
- `no_show`

Every event must contain:
- tenant;
- visit;
- authenticated actor;
- actor context;
- occurred_at;
- correlation_id;
- source/destination context where applicable.

Event rows are immutable evidence; clients never edit them directly.

## 5. Queue data semantics

D2 `patient_flow_queue_entries.position` is normalized by D3 to a contiguous Reception order beginning at 1 within each active `tenant_id + operating_date + lane_key` group.

Known existing Queue lanes are reused:
- `general`
- `doctor`
- `urgent`

D3 does not introduce a new queue engine or redefine the meaning of the existing lane identifiers.

Reception handoff after clinical finish uses:
- `lane_key=general`
- `routing_target=reception`

This avoids introducing a new queue lane solely for the pending-close state.

## 6. Work Session semantics

D2 Work Session status:
- `active`
- `finished`
- `held`
- `transferred`
- `cancelled`

D3 lifecycle projection uses:
- clinical start → `active`;
- normal clinical finish → `finished + outcome=finish`;
- cancellation of active work → `cancelled`.

D3 does not create a new Visit state for held/transferred.

Existing legacy Hold/Resume functions must not remain an untracked lifecycle authority. Their callers are audited and migrated or explicitly retained only when their behavior is represented through the D3 contract.

## 7. Idempotency and concurrency

`p_correlation_id` is the command correlation/idempotency key.

D3 will enforce:
- one logical command outcome for one tenant/correlation identifier;
- no duplicate active Queue Entry per Visit;
- no duplicate active Work Session per Visit;
- competing clinical starts are serialized by locking and database constraints;
- retries return the existing command outcome when the same correlation identifier has already been completed.

If a command has a semantic reason not to retry successfully, that error must be explicit and tested. No silent duplicate behavior is allowed.

## 8. Transaction boundary

Each lifecycle command is one database transaction.

No intermediate state is exposed as successful to the caller.

A successful response is returned only after:
- legacy Visit compatibility state;
- D2 Work Session / Queue Entry projection;
- Event evidence

are committed together.

## 9. Security boundary

D3 command functions are privileged database operations and must:
- derive actor from the authenticated context;
- resolve tenant from the canonical tenant mechanism;
- validate effective permission;
- validate subject ownership/tenant;
- use a controlled search_path;
- have explicit function ACLs;
- not be executable by `anon`;
- not rely on user-editable JWT user metadata for authorization.

The application-facing function surface is intentional; the functions are not generic arbitrary-write RPCs.

## 10. API adapter rule

Existing UI/server actions will become thin adapters over the D3 commands.

The adapter may:
- validate shape;
- pass the authenticated request;
- map deterministic command errors to existing UI messages;
- revalidate relevant paths.

The adapter may not:
- perform its own lifecycle write;
- create a second transition map;
- create a second lock authority;
- create D2 rows independently.
